# Host adapter

pstack skills are written against capabilities, not against one agent product. This file is the
only place that names concrete tools, paths, and vendor features. A skill that needs a capability
links here instead of hardcoding a vendor tool name.

Read this file once per session, the first time a skill references a capability you have not yet
resolved. Resolve each capability against the host you are actually running in. When a capability
is absent, take the fallback in the same row. A missing capability degrades a skill; it never
blocks one.

## Capabilities

| Capability | What a skill needs it for | Resolve it as | Fallback when absent |
|---|---|---|---|
| `SPAWN_SUBAGENT` | Fan-out, delegation, review panels | Your host's subagent tool (`Task`, `Agent`, `spawn_agent`, `dispatch_agent`, `subagent`) | Run the sub-tasks yourself in sequence, one at a time, summarizing each before the next |
| `SUBAGENT_MODEL` | Assigning a role to a specific model | The model parameter on the subagent tool | Ignore every model choice in the skills, run one model, and say so in the reply |
| `SUBAGENT_TYPE` | Routing a delegate to a preset agent persona | The agent-type parameter (`subagent_type`, `agentType`, `agent`) | Inline the persona's instructions into the subagent prompt |
| `BACKGROUND_AGENT` | Long work that outlives the turn | Background or remote execution (`run_in_background`, cloud/remote agents, detached runs) | Run in the foreground and shorten the unit of work |
| `ASK_USER` | Structured multiple-choice questions | Your host's question tool (`AskQuestion`, `AskUserQuestion`) | Ask in plain prose, numbered options, one round |
| `TRANSCRIPTS` | Reading this session's or a prior session's record | See [Transcripts](#transcripts) | Skip transcript mining. Say you skipped it, and use git history, PRs, and tickets instead |
| `SKILL_PATHS` | Finding, writing, and installing skills | See [Skill locations](#skill-locations) | Write the skill to `./skills/<name>/SKILL.md` in the project and tell the user how to install it |
| `MODEL_CONFIG` | Per-role model overrides | `~/.pstack/models.md`, see [Model configuration](#model-configuration) | Use each skill's inline default models |
| `SCHEDULED_WAKE` | Re-checking a condition until it holds | A loop or scheduling primitive: a host loop command, a cron tool, a CI schedule, or a watcher subagent | A watcher subagent that polls and reports, or a single pass plus an explicit "re-run me" instruction |
| `MCP_DISCOVERY` | Listing which evidence sources are reachable | Your host's tool list or tool-search facility | Ask the user which sources are connected, then query only those |
| `WEB` | Fetching a URL or searching | Any web fetch or search tool | Ask the user to paste the content |
| `SKILL_AUTHORING` | Writing a new `SKILL.md` | Your host's skill-authoring skill if it ships one (names vary: `create-skill`, `skill-creator`, `skill-builder`) | [Authoring conventions](#authoring-conventions) below |
| `REVIEW_BOT` | Triaging automated PR review comments | See [Review bots](#review-bots) | Treat every review comment as human-authored and triage on merits |
| `APP_CONTROL` | Driving the real app to prove behavior | The project's `verify-<app>` skill, generated by **create-verification-skill** | Generate one with `/create-verification-skill`, or drive the app by hand and record the commands |
| `PROSE_CLEANUP` | Stripping AI tells before commit | The bundled **unslop** skill | None needed; **unslop** ships with pstack |

## Transcripts

Several skills (**recall**, **reflect**, **automate-me**, **show-me-your-work**, and the Session
pickup and Eval playbooks) read agent transcripts. Every host stores these differently, and some
do not expose them at all.

Resolve the path in this order:

1. `PSTACK_TRANSCRIPTS_DIR`, when the user has set it.
2. A transcript or session directory named in your system prompt for the **active workspace**.
3. The host's own convention, when you can confirm it by listing the directory:
   - `~/.claude/projects/<slugified-workspace-path>/`
   - `~/.cursor/projects/<slugified-workspace-path>/agent-transcripts/`
   - `~/.codex/sessions/`
   - A `sessions/`, `history/`, or `transcripts/` directory under the host's config root.

   Slugified workspace path means the absolute path with the leading `/` dropped and every `/`
   replaced by `-`, so `/Users/you/proj` becomes `Users-you-proj`.
4. No transcripts. Say so and continue without them.

**Scope rule, and it is not optional.** Read only the active workspace's transcripts. Never glob
across the sibling project directories of other workspaces. That crosses workspace boundaries and
reads private conversations from unrelated projects. Order candidates by real modification time
(`ls -t`), never by the UUID in the filename.

## Skill locations

Skills are installed in one of three scopes. The directory names differ per host; the scopes do
not. Discover the real ones by listing the candidates below before you write anything.

| Scope | Meaning | Common locations |
|---|---|---|
| Project | Checked into the repo, applies to this workspace | `.agent/skills/`, `.claude/skills/`, `.cursor/skills/`, `./skills/` |
| User | Personal, applies to every workspace | `~/.agent/skills/`, `~/.claude/skills/`, `~/.cursor/skills/` |
| Plugin | Installed as a bundle, read-only in practice | `~/.claude/plugins/`, `~/.cursor/plugins/`, and the directory this file lives in |

When a skill tells you to write a project-local skill, write it to the project scope directory
that already exists in the repo. When none exists, create the one matching the host you are
running in, and name the path in your reply so the user can move it.

`PSTACK_SKILLS_DIR` overrides the project scope when set.

## Model configuration

Per-role model choices live in `~/.pstack/models.md`, written by the **setup-pstack** skill. A
project-local `.pstack/models.md` overrides it. Both are plain text: one `role: model` line per
role, `#` for comments, list values comma-separated.

Read the file when a skill references a role. When the file is absent, or the role has no line,
use the skill's inline default. A value of `inherit-parent` or `auto` means the role runs on the
parent chat model: omit the model parameter entirely rather than naming a slug.

Hosts that support always-applied instruction files can mirror this config into one, so it loads
without an explicit read. That mirror is a convenience. `~/.pstack/models.md` stays the source of
truth, because it is the file every host can read.

## Review bots

Automated reviewers comment on pull requests under a bot account. Which one you face depends on
the repo, not on the agent you are running in. Known logins and body markers:

| Bot | Author login contains | Body markers |
|---|---|---|
| Cursor Bugbot | `bugbot`, or `cursor` with a bot-shaped body | `bugbot`, `cursor_automation_id`, `agentic security review` |
| GitHub Copilot review | `copilot` | `copilot` |
| CodeRabbit | `coderabbit` | `coderabbit` |
| Greptile | `greptile` | — |
| Generic | `bot`, `-bot`, `[bot]` | `security review`, `review automation` |

`PSTACK_REVIEW_BOTS` overrides this list: a comma-separated set of author-login substrings.

The triage posture is in `../poteto-mode/references/review-bot-triage.md` and applies to all of
them. Bot findings are claims to verify, not tasks to execute.

## Authoring conventions

Use these when the host has no `SKILL_AUTHORING` skill of its own.

A skill is a directory holding `SKILL.md`, plus optional `references/`, `playbooks/`, and
`scripts/` subdirectories it links relatively.

`SKILL.md` frontmatter carries two required keys:

```yaml
---
name: skill-name
description: What it does, then when to use it, naming the literal phrases that should trigger it.
---
```

`name` is lowercase, hyphenated, and matches the directory. `description` is one YAML scalar; quote
it or use `>-` with indented continuation when punctuation demands it. It is the only thing an
agent sees when deciding whether to load the skill, so it names concrete trigger phrases rather
than a topic.

Optional keys, ignored by hosts that do not know them:

```yaml
license: MIT
allowed-tools: Read, Grep, Glob
metadata:
  invocation: explicit
```

`metadata.invocation: explicit` means the skill applies only when the user invokes it by name or
slash command, never on description matching alone. Hosts with a native equivalent should map it
onto that field; hosts without one should treat the skill as opt-in and say so in the skill body.

Then write the body: a title, the operating rules, and the steps. Address the next agent, not a
human reader. It arrives cold, with no memory of this conversation. Link sibling files relatively.
Test the skill by running it on a real task before you ship it, and revise from what the run
actually did rather than from what you meant it to do.
